IMPLEMENTATION PLAN

VS Code extension plan

Plan for a docserve server manager as a VS Code extension.

Scope

What v1 does — decided up front to keep the first release small.

In scope

Start / stop docserve from the status bar and command palette, see what's running, open the gallery in the browser. The extension is a thin client over the CLI — no server code inside the extension.

Out of scope (v1)

WebView gallery / live preview inside the editor, gallery custom UI, editing server code. A WebView preview is the natural Phase 2 of the project, once server control is stable.

Design decisions

CLI as a subprocess

Start via docserve <dir> --background (spawned detached), stop via docserve stop [dir]. Single source of truth for serving logic; the extension ships no server.

State files as the source of truth

Running servers self-report to ~/.docserve/state/*.json (pid, port, url, docsDir). The extension reads them (pid-liveness checked), so servers started from the CLI or the menu bar app appear too.

Refresh: watcher + polling

The CLI has no push channel, so the state dir is watched with fs.watch plus a slow (5s) poll as a safety net. Status bar updates on change only.

Cross-platform open

The CLI's --open is macOS-only today, so the extension never passes it — it opens the gallery itself with vscode.env.openExternal (macOS / Windows / Linux).

Multi-root aware

Single-folder workspace: served directly. Multi-root: QuickPick asks which folder. The extension never assumes "the" workspace folder.

Resolving npx

GUI-launched VS Code may miss PATH entries. The extension resolves the runner (homebrew, nvm, volta, system) and falls back to a user override setting before failing with guidance.

Commands & settings

CommandBehavior
docserve.startServe a folder (current workspace folder, folder picker on conflict/none). Waits for the state file, then offers to open the gallery.
docserve.openOpen the gallery URL of the picked running server in the browser.
docserve.stopStop a server (QuickPick lists running ones; scoped to the workspace folder first).
docserve.stopAllStop every running docserve server.
docserve.listShow running servers (QuickPick: open / stop rows, one per instance).
SettingDefaultDescription
docserve.port4242Preferred port passed as --port (the CLI falls back +1 up to 20 tries).
docserve.cliCommandnpx -y @noy4/docserveCommand used to run the CLI, overridable for global installs or custom paths.
docserve.stateDiremptyOverrides the state dir (sets DOCSERVE_HOME); mainly for tests.

Status bar item (per workspace): $(radio-tower) docserve when idle, $(radio-tower) :4242 filled when this folder is being served. Click opens docserve.list (start entry included).

Roadmap

Phase 1 — Extension scaffold P1
A vscode/ package in the monorepo that activates, registers command stubs, and shows a status bar placeholder.
Monorepo layout
vscode/ beside cli/ and desktop/ — package.json, tsconfig, esbuild bundling, npm scripts
Contribution points
commands, configuration, status bar item; activation on onStartupFinished so status renders immediately
Icon & listing assets
reuse the app icon; marketplace README drafted from the docserve docs
Phase 2 — State reader P1
Read live instances from the state dir — the extension's eyes, independent of how servers were started.
State parsing
read ~/.docserve/state/*.json, validate shape, check pid liveness, ignore stale entries (no pruning — that's the CLI's job)
Watcher + poll
fs.watch on the state dir plus a 5s fallback poll; debounced status bar refresh
DOCSERVE_HOME
honor the override (also settable via docserve.stateDir) so tests stay isolated
Phase 3 — Server control P1
Start, stop, and open — each a thin subprocess call away.
Start
spawn --background detached, wait for the state file with a progress toast; "already serving" opens the URL instead
Stop / stop all
docserve stop [dir] per folder or everything, with confirmation-free UX (stopping is cheap to undo)
Open gallery
vscode.env.openExternal on the instance URL — never the CLI's --open
Runner resolution
find npx/node across PATH gaps (homebrew, nvm, volta), honor docserve.cliCommand, clear error if Node is missing
Phase 4 — Status bar & QuickPick UX P1
The daily-driver surface: glanceable status, one click to act.
Status bar states
per workspace — idle / serving (port shown) / starting…, tooltip listing the url; theme-consistent colors
Instance QuickPick
one row per running server (docs dir + url) with Open / Stop actions, plus Start and Stop all
Folder resolution
single-root workspace serves directly, multi-root asks, no workspace opens a folder dialog
Phase 5 — Settings & polish P2
Configuration surface and the small comforts.
Settings
docserve.port, docserve.cliCommand, docserve.stateDir wired through
Output channel
subprocess stdout/stderr logged to a "docserve" output channel for diagnosis
Error UX
actionable messages: Node missing, port exhausted, CLI older than state format
Phase 6 — Tests P2
Same rigor as the CLI: pure logic unit-tested, flows integration-tested.
Unit tests
state parsing, pid liveness, runner resolution — plain node --test
Integration tests
@vscode/test-electron runs commands against a fake CLI script with DOCSERVE_HOME isolation
Phase 7 — Marketplace publish P2
noy4.docserve on the VS Code Marketplace, published from CI.
Packaging
vsce package with bundled extension (esbuild), icon, license, repository links
Release workflow
tagging vscode-v* publishes via @vscode/vsce with a VSCE_PAT secret, mirroring the cli-v* npm flow
Docs wiring
landing page and README get an install link (ext install noy4.docserve)

Decisions

QuestionDecision
Minimum CLI version?None. The extension reads the state format as-is and warns on a failed start rather than hard-pinning a version.
Auto-start a server when opening a workspace with index.html?No — surprising actions are worse than one extra click.
Per-workspace or global status bar?Per workspace: each window reflects its own folder's state only; the QuickPick carries the full instance list.
Version schemeThe extension starts at 0.1.0, independent of the CLI's 0.3.x.

Notes

F5 can hang on this machine

localhost resolves to IPv6 first, so js-debug never attaches and the host stops on the first line. Use ⌃F5 (Run Without Debugging) or launch via CLI: code --extensionDevelopmentPath=.../vscode --disable-extensions --new-window.
